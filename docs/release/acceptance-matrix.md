# Acceptance matrix

Maps each PRD acceptance scenario (§13, AT-01..18) and non-functional requirement (§12, NFR-01..16)
to the tests that exercise it today and to the evidence the release gate needs. The release
checklist ([release-checklist.md](release-checklist.md)) reads its "all AC/AT pass with evidence"
gate from this page.

**No row has passed yet.** A row becomes "Đạt" only when a run of the stated tests or procedure on a
release build has stored evidence, and the row links it with the run date.

## Status values

| Status | Meaning |
|---|---|
| Chưa chạy | Nothing tests this yet, or the procedure has never been run. |
| Có test tự động một phần | Automated tests cover part of the scenario; the end-to-end acceptance spec is not written or not run. |
| Đã viết spec, chưa chạy | The end-to-end acceptance spec is written but has never run on a real stack; the selectors and request bodies it assumes are unconfirmed (named in the notes). |
| Thủ công | A manual check on devices or by a reviewer; needs a recorded run. |
| Bị chặn | Cannot pass until a missing command, file or owner decision lands (named in the notes). |
| Đạt | Passed on a release build with linked evidence. |

## Running the acceptance specs

[`apps/web/e2e/acceptance/`](../../apps/web/e2e/acceptance/) holds one spec per scenario
(`at-NN-*.spec.ts`, linked per row below) and the shared fixtures
[`fixtures/acceptance.ts`](../../apps/web/e2e/acceptance/fixtures/acceptance.ts). The specs pass
typecheck and lint, and `playwright test --list --project acceptance` lists every scenario plus
the owner sign-in setup, but **none has run on a real stack yet**. The unconfirmed assumptions of
each spec are in its row; the [tester report](../../plans/reports/tester-261019-0704-acceptance-specs.md)
has the full list.

- Command: `make acceptance` from the repository root, or `corepack pnpm e2e:acceptance` in
  `apps/web`.
- Stack: `make dev` running, data from `make seed` (`tally seed dev`), and `E2E_OWNER_PASSWORD`
  set (`E2E_OWNER_EMAIL` too when the owner is not the seeded default).
- `E2E_LEDGER_VERIFY_CMD`: a shell command that runs `tally ledger verify` against the stack's
  database as the application role (the API's `DATABASE_URL`; verify refuses a superuser or a
  role that bypasses row level security). Each journey ends by running it with `--tenant <id>` and expects `0 mismatches`. When
  the variable is unset the step is skipped with a `skipped-step` annotation and the test can
  still be green.
- Some scenarios need a prepared stack or a second store; their rows name the variables, and the
  spec skips with the missing variable's name.
- Data: the journeys write real documents to the store they sign in to, so a run by hand uses the
  sandbox `cua-hang-a-demo` (`tally seed demo --parent cua-hang-a`), not `cua-hang-a`. AT-10,
  AT-11, AT-13 and AT-18 skip unless `APP_ENV=test` is set, and run only on a throwaway stack
  started with it.
- **A scenario counts as passed only when its spec passed with the ledger verify step run**: no
  `skipped-step` annotation and `0 mismatches` in the output.
- Nightly CI: the `e2e-nightly` job in [`ci.yml`](../../.github/workflows/ci.yml) runs
  `make acceptance` with `E2E_LEDGER_VERIFY_CMD` set and keeps the evidence of every run, passing
  or not, as the `acceptance-evidence` artifact. The job sets `APP_ENV=test` and the
  application role's `DATABASE_URL` for the verify command, so AT-10, AT-13 and AT-18 run there.
  AT-11 still skips: it also needs the API started with `TALLY_FAULT_INJECT` and
  `E2E_FAULT_INJECT_ARMED=1`, which the job does not set, so it needs a separate run. This set-up
  has never run on CI yet.

## Evidence

- Runs write their artifacts to uncommitted directories: `make acceptance` records a trace and
  screenshots of every test in `apps/web/e2e/acceptance/evidence/<date>/` (the run day in
  Asia/Ho_Chi_Minh, git-ignored), and writes the HTML report to `apps/web/playwright-report/`
  only when `CI` is set; the k6 summaries of `make load-test` and `make soak-test` go to
  `load/test-results/`, and the restore drill report to `test-results/restore-drill/`. Keep the
  `tally ledger verify` output with them, archive the set with the CI run (the nightly
  `acceptance-evidence` artifact) or the release ticket, and link the archive here.
- Manual runs are recorded as reports in `plans/reports/`, as described for devices in
  [device-browser-matrix.md §5](../operations/device-browser-matrix.md#5-recording-results).
- Evidence must not contain cookies, tokens, passwords or pilot customer data.

Existing API integration tests run with `make test-integration`; the other Playwright specs run
with `make e2e`.
